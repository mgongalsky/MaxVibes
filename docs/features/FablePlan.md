Давай сначала критику, потом твои четыре идеи в порядке моего голосования.

**Критический взгляд на MaxVibes сегодня.** Сильная сторона очевидна: PSI-операции + контролируемый канал команд + approve-гейт — этого нет ни у Cursor, ни у голого Claude Code. Слабые места, честно:

1. **Модель работает вслепую после правок.** Она применила модификации — и не знает, скомпилировалось ли. Узнаёт, только если ты вручную прикрепишь Errors или она догадается попросить `gradlew build` (минута на JVM-старт ради проверки синтаксиса). А у тебя под рукой IntelliJ с его инспекциями: **автоматический фидбек «применили модификации → через N секунд хайлайтер дал ошибки → они сами уезжают в следующий ход»** — это замыкание петли, которое качественно меняет автономность. У тебя уже есть `ideErrorsPort.getCompilerErrors()` — осталось дёрнуть его после apply и подшить в `commandResults`-подобное поле. Я бы ставил это выше всех четырёх твоих идей.

2. **Реджект без хирургии.** Сейчас отказ — всё или ничего: пять модификаций, четыре хорошие, одна кривая — либо принимаешь всё, либо печатаешь «переделай №3». Чекбоксы на Proposed-списке (применить выбранные, остальные reject с фидбеком) — дёшево и сильно.

3. **`FIND_USAGES` так и висит.** Ты сам его называл открывающим новый класс операций — а модель до сих пор не может спросить «кто зовёт этот метод» и правит сигнатуры вслепую. Это read-инструмент, канал `requestedViews` уже готов под расширение (granularity=USAGES).

Теперь твои идеи, моё голосование: **диффы → картинки → skills → PSI-фишки.**

**Диффы — да, и твоя интуиция про «просто обозревать диффы непонятно» архитектурно попадает в яблочко.** Потому что у тебя есть то, чего нет у текстовых тулов: модификация — это не unified diff, а **типизированная операция с ElementPath**. То есть «что предлагается» само знает своё место в коде. Дизайн: в Proposed-списке каждая строка кликабельна (навигация у тебя уже есть — `onNavigateToPath`), а рядом иконка «👁 diff» открывает **IntelliJ'шный DiffManager** с per-element диффом: слева текущий элемент (достаём PSI-навигатором по path), справа — `content` из модификации. Не diff всего файла, а именно того метода/класса, о котором речь — контекст автоматом. Для CREATE — слева пусто, для DELETE — справа. Технически: `DiffManager.getInstance().showDiff(project, SimpleDiffRequest(...))` с двумя `DiffContent`, ~150 строк вместе с извлечением текущего текста элемента. Это идеальная пара к approve-гейту: Proposed → глянул диффы → снял чекбокс с кривой → Approve.

**Картинки — да, вторым номером, и это дешевле, чем кажется.** Claude Code в stream-json режиме принимает image content blocks (base64) в user message — то есть транспорт уже умеет, вопрос только в нашем протоколе. Дизайн: кнопка 📎/paste-from-clipboard в поле ввода (у тебя уже есть паттерн attachedTrace — картинка это attachedImage рядом), в `ClipboardRequest` поле `attachedImages: List<String>` (base64), адаптер кладёт их image-блоками в content. Для clipboard-режима — честное «не поддерживается» (человек и так может вставить картинку в claude.ai руками). Скриншот UI-бага + «почини вот это» — киллер-юзкейс для плагина, который сам рисует UI.

**Skills — идея правильная, но я бы резал скоуп.** «Более-менее нативно» с разбиением на подзадачи — это оркестрация, отдельный большой проект с своим состоянием, и он потянет за собой всё (у тебя уже есть specificPrompt — это же прото-skill). Минимальный шаг, дающий 70% ценности: **каталог skills как файлов** `.maxvibes/skills/*/SKILL.md` (совместимо по формату с клод-кодовскими скиллами — сможешь таскать готовые), селектор в UI вместо/рядом с specificPrompt, выбранный скилл подмешивается в системник хода. Без автодекомпозиции — её модель и так делает сама, если скилл описывает процесс. Оркестратор — отдельным спринтом, когда упрёшься.

**PSI-фишки — вечнозелёное, но конкретизирую топ-3** вместо «чего-нибудь»: (1) `FIND_USAGES` как view-granularity — см. выше; (2) **RENAME как модификация** — `RenameProcessor` у тебя изучен, а сейчас модель переименовывает через N × REPLACE_ELEMENT, теряя вызовы; (3) отдать модели **структурную валидацию до apply**: прогон `content` через KtPsiFactory на parse-ошибки в момент Proposed — кривой Kotlin ловится до Approve, а не после.

Мой порядок на ближайшие спринты: **(1) авто-фидбек ошибок после apply → (2) per-element diff + чекбоксы на Proposed → (3) картинки → (4) skills-каталог → (5) FIND_USAGES/RENAME.** Первое — маленькое и умножает всё остальное; второе-третье — твои идеи, дозревшие до дизайна; четвёртое-пятое — по мере аппетита.

С чего начинаем? Если согласен с порядком — давай спланирую авто-фидбек: там надо аккуратно решить, когда снимать снапшот ошибок (сразу после apply хайлайтер ещё не дожевал — нужен debounce или DaemonListener) и как не заспамить модель ворнингами.
