# Streaming logs : исключить многократную запись полного накопленного payload

## Проблема

Логи взаимодействия с coding -agent / LLM очень быстро разрастаются во время streaming - ответов.На каждый небольшой новый фрагмент текста — иногда буквально несколько символов — в лог повторно записывается большая полная строка события или весь накопленный streaming payload.В результате одни и те же данные многократно дублируются:

-размер логов растёт значительно быстрее фактического ответа модели;
-чтение и анализ логов становятся тяжёлыми;
-большие лог -файлы плохо обрабатываются инструментами;
-IDE может зависать при записи, открытии или отображении таких логов;
-диагностика реальных событий теряется среди повторяющегося streaming - шумa.

## Требуемое поведение

        Логирование streaming -событий должно быть компактным и пропорциональным объёму реально полученных новых данных.

-Не писать полный накопленный текст ответа при каждом streaming chunk .
-Для промежуточного события логировать только новый delta / chunk либо компактные метаданные события.
-Полный итоговый текст при необходимости логировать один раз после завершения сообщения / turn.
-Не дублировать большие неизменившиеся поля протокола в каждом событии.
-Сохранять достаточно информации для диагностики порядка событий, типов событий, ошибок и завершения stream .
-Не выводить reasoning / thinking или чувствительные данные шире, чем это уже разрешено текущей политикой логирования.
-Ограничить или безопасно сокращать аномально большие одиночные payloads с явной пометкой о truncation.

## Предлагаемый формат

        Для промежуточного chunk достаточно компактной записи наподобие:

```text
STREAM_DELTA session =<id> turn =<id> type = text chars = 3 delta ="abc"
```

Для больших delta:

```text
STREAM_DELTA session =<id> turn =<id> type = text chars = 842 preview ="..." truncated =true
```

После завершения stream:

```text
STREAM_COMPLETE session =<id> turn =<id> chunks =124 textChars =18420 durationMs =...
```

Полный финальный payload стоит записывать только если он действительно нужен для восстановления / диагностики и только один раз . Если финальный ответ уже сохраняется в transcript / session storage, повторная полная запись в технический лог может быть не нужна .

## Вариант реализации

        1.Разделить raw protocol logging и обычный диагностический logging .
2.В обычном режиме писать только тип события, delta - размер, идентификаторы и компактный preview .
3.Добавить opt -in debug / trace режим для сырого протокола, если он действительно нужен при расследовании ошибок.4.Не собирать лог - сообщение с полным payload, если текущий log level его всё равно не запишет.5.Финальную статистику stream писать один раз : число chunks, размер ответа, длительность и результат завершения .
6.При наличии отдельного raw session log рассмотреть ротацию и максимальный размер файла .

## Тестовые сценарии

        1.Stream из 1000 chunks по 3 символа не создаёт лог, содержащий 1000 копий растущего полного ответа.2.Общий объём промежуточных записей остаётся порядка фактического объёма delta либо меньше.3.Финальное событие и ошибки остаются видимыми и диагностируемыми .
4.Большой одиночный chunk сокращается согласно лимиту и помечается как truncated .
5.Отключённый debug / trace режим не сериализует и не форматирует полный raw payload без необходимости.6.Claude Code и Codex используют одинаково безопасную семантику логирования.7.Проверяется отсутствие тройного дублирования одного события в нескольких логгерах.8.Открытие полученного после длинной сессии лог -файла не приводит к заметному зависанию IDE.

## Критерии готовности

        -Каждый streaming chunk не приводит к повторной записи всего накопленного ответа.
-Размер лога растёт линейно относительно новых данных, а не квадратично относительно длины ответа .
-Основной лог остаётся компактным и пригодным для диагностики .
-Сырой протокол, если он нужен, доступен только в явно включённом debug / trace режиме.
-Добавлены тесты или воспроизводимый benchmark, подтверждающие существенное уменьшение размера логов.
